# 项目服务周期与项目中心 CRUD 设计

## 背景

当前项目中心已经支持：

- 新建项目
- 为项目新增或绑定设备
- 上传项目附件
- 从客户中心反查项目和设备详情

但还缺两类核心能力：

1. 项目设备需要支持“服务周期”管理，用于区分新上设备和续保旧设备，并据此判断保内保外
2. 项目中心只支持新增，缺少完整 CRUD，无法对项目本身、项目设备、项目附件做完整维护

## 目标

本次需求目标如下：

1. 在项目中心给项目新增设备时，支持区分：
   - 新上设备
   - 续保旧设备
2. 服务周期采用：
   - `service_start_date`
   - `service_end_date`
3. 服务周期记录保存在 `ProjectDevice` 上，而不是 `Device` 主表
4. 客户中心和设备详情中的保内保外状态，取该设备最近一条项目服务记录计算
5. 项目中心补齐 CRUD：
   - 项目新增、编辑、软删除
   - 项目设备新增、编辑、删除
   - 项目附件上传、预览、下载、删除
6. 合同文件先继续作为项目附件处理，不单独做合同业务关系

## 非目标

本次不做以下内容：

- 不引入独立的维保管理模块
- 不新增独立的设备服务记录表
- 不恢复或扩展项目与合同的业务关联关系
- 不修改客户中心的整体结构，只补充服务周期字段展示

## 方案选型

### 方案 A：服务周期记在 `Device` 主表

优点：

- 判断当前保内保外最直接

缺点：

- 续保会覆盖旧值，历史不清晰
- 无法自然表达“哪一个项目做了这次续保”

不采用。

### 方案 B：服务周期记在 `ProjectDevice`

优点：

- 每次项目设备关系天然保留历史
- 新上设备和续保旧设备都能用同一结构表达
- 不需要新增独立服务记录表

缺点：

- 客户中心和设备详情里的“当前保内保外”需要从最近一条项目服务记录推导

采用本方案。

### 方案 C：新增独立服务记录表

优点：

- 语义最完整，长期扩展性最好

缺点：

- 这轮开发复杂度明显变高
- 对当前项目流程来说过度设计

本次不采用。

## 核心设计

### 一、数据模型

在 `ProjectDevice` 上新增以下字段：

- `service_type`
- `service_start_date`
- `service_end_date`

其中：

- `service_type` 取值建议：
  - `new_install`
  - `renewal`

含义：

- `new_install`：这次项目新上设备
- `renewal`：这次项目对旧设备做续保服务

保留现有字段：

- `project`
- `device`
- `quantity`
- `deploy_location`
- `device_project_type`
- `usage`

这样 `ProjectDevice` 既描述“项目绑定了什么设备”，也描述“这次项目对这台设备的服务周期是什么”。

### 二、保内保外判断规则

统一规则：

1. 找到该设备所有有效的 `ProjectDevice`
2. 取“最近一条服务记录”
3. 如果今天落在 `service_start_date` 到 `service_end_date` 之间，则显示 `保内`
4. 否则显示 `保外`

最近一条服务记录的排序建议：

1. `service_end_date` 最大
2. 若相同，则按 `updated_at` 或 `id` 倒序兜底

### 三、项目中心设备新增流程

#### 1. 新上设备

在项目设备新增区域先选择：

- 新上设备

流程：

1. 选择产品型号
2. 录入设备名称、序列号等基础信息
3. 录入服务开始日期和服务结束日期
4. 保存后：
   - 创建设备
   - 创建 `ProjectDevice`

#### 2. 续保旧设备

先选择：

- 续保旧设备

流程：

1. 只能从当前客户已有设备中选择
2. 选中后自动带出设备已有信息
3. 用户重点填写：
   - 服务开始日期
   - 服务结束日期
   - 本次项目里的部署/备注等
4. 保存后：
   - 不新建设备
   - 只新增一条新的 `ProjectDevice`

这样同一台设备可以在不同项目里保留多条服务记录。

## CRUD 设计

### 一、项目 CRUD

项目中心补全以下能力：

- 新增项目
- 编辑项目基础信息
- 软删除项目

删除语义继续沿用现有软删除风格，不做硬删除。

### 二、项目设备 CRUD

项目详情中的项目设备应支持：

- 新增
- 编辑
- 删除

编辑范围建议包含：

- 服务类型
- 服务开始日期
- 服务结束日期
- 部署位置
- 项目类型
- 备注及设备可编辑扩展字段

删除语义建议为：

- 删除当前 `ProjectDevice` 关系
- 不删除设备主表记录

### 三、项目附件 CRUD

项目附件应支持：

- 上传
- 预览
- 下载
- 删除

合同文件暂时继续作为项目附件处理，不再在项目中心单独维护“关联合同”业务对象。

## 接口设计

### 一、后端

需要扩展：

- `ProjectDeviceSerializer`
- `project_overview`
- 项目、项目设备、附件相关视图

建议在 `project_overview` 返回的 `devices` 中增加：

- `service_type`
- `service_start_date`
- `service_end_date`
- `service_status`

其中 `service_status` 为后端计算后的：

- `保内`
- `保外`

客户中心和设备详情相关接口也应补充：

- 当前服务开始日期
- 当前服务结束日期
- 当前服务状态

### 二、前端

项目中心页面需要补：

- 项目编辑入口
- 项目删除入口
- 项目设备编辑入口
- 项目设备删除入口
- 项目附件删除入口
- 服务类型选择
- 服务开始/结束日期输入

客户中心需要补：

- 设备列表中的保内保外字段
- 设备详情中的当前服务周期展示
- 项目详情中的项目设备服务周期展示

## 前端交互建议

### 一、项目列表

项目列表操作列增加：

- 编辑
- 删除
- 详情

### 二、项目详情里的项目设备

项目设备列表增加字段：

- 服务类型
- 服务开始日期
- 服务结束日期
- 保内保外

操作列增加：

- 详情
- 编辑
- 删除

### 三、设备新增表单

设备新增表单先选：

- 新上设备
- 续保旧设备

选择续保旧设备时：

- 设备基础字段只读或默认带出
- 核心关注本次服务周期

## 错误处理

- 服务结束日期不得早于服务开始日期
- 续保旧设备时，必须从当前客户已有设备中选
- 新上设备时，设备型号和序列号必填
- 删除项目时，如果仍有关联项目设备或附件，允许软删除，但详情不再在主列表展示
- 编辑项目设备时，只影响当前项目设备记录，不回写其他项目的服务周期

## 测试策略

### 后端测试

新增或扩展测试覆盖：

- `ProjectDevice` 服务周期字段校验
- `project_overview` 返回服务字段
- 设备当前保内保外取最近服务记录计算
- 项目软删除
- 项目设备删除不影响设备主表
- 项目附件删除

### 前端测试

至少覆盖工具和数据映射层：

- 服务状态显示逻辑
- 服务开始/结束日期的校验逻辑
- 新上设备与续保旧设备的表单切换逻辑

## 结论

本方案采用“服务周期挂在 `ProjectDevice` 上”的方式，兼顾历史保留和当前需求复杂度。当前保内保外状态通过最近一条项目服务记录推导，能够满足客户中心、设备详情、项目详情的一致展示需求，同时为项目中心补齐 CRUD 能力。
