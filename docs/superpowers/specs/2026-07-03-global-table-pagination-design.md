# 全系统表格统一分页设计

## 背景

当前系统内多个模块的列表页和详情内子列表都以单页全量展示，数据增长后会带来以下问题：

- 页面纵向拉伸严重，查找和定位效率低。
- 搜索结果无法与页码联动，用户只能在超长列表中继续滚动。
- 不同模块的列表交互不一致，后续扩展排序、筛选和导出时成本偏高。

本次目标是在不影响左侧组织树、树形选择器等结构的前提下，为全系统所有表格型列表提供统一分页能力。

## 范围

### 纳入分页的表格

1. 客户中心
   - 客户详情 tab 内的联系人、负责销售、已购设备、关联合同、关联项目表格
2. 项目中心
   - 项目主列表
   - 项目详情内的项目设备、关联合同、项目附件表格
3. 设备中心
   - 设备主列表
4. 销售中心
   - 销售主列表
   - 销售详情内客户、设备、合同等表格（如当前页面存在）
5. 产品中心 / 产品型号
   - 产品主列表
   - 产品型号主列表
   - 其他同类表格型列表

### 不纳入分页的结构

1. 客户中心左侧组织树
2. 各类树形下拉选择器
3. 明显属于树状浏览而非表格浏览的组件

## 交互要求

### 统一分页方式

所有表格统一使用传统分页：

- 页码切换
- 每页条数切换
- 总数展示
- 默认每页 `10` 条
- 可选每页条数建议为 `10 / 20 / 50`

### 分页行为规则

1. 初次进入页面时默认加载第 `1` 页。
2. 修改搜索条件后回到第 `1` 页。
3. 切换 tab 后回到当前 tab 的第 `1` 页。
4. 切换客户、项目、销售等上下文对象后，相关子表格回到第 `1` 页。
5. 修改每页条数后回到第 `1` 页。
6. 删除当前页最后一条记录后，如果当前页已无数据且不是第一页，应自动回退到上一页。

### 布局要求

1. 分页控件放在表格底部。
2. 分页区右对齐，避免破坏现有标题和筛选区布局。
3. 表格为空时保留分页区域位置，避免页面跳动过大。
4. 搜索、筛选、分页同时存在时，分页永远作用于当前查询结果，而不是全量数据。

## 后端设计

### 分页协议

统一使用分页响应结构：

```json
{
  "count": 128,
  "page": 1,
  "page_size": 10,
  "total_pages": 13,
  "results": []
}
```

请求参数统一为：

- `page`
- `page_size`
- 其他原有过滤参数，例如 `search`、`person_type`、`product_line` 等继续保留

### 实现原则

1. 主列表接口统一接入同一套分页器，避免各模块各自实现。
2. 原有搜索逻辑保留，分页在过滤结果之后生效。
3. 默认分页参数缺省时返回第 `1` 页、每页 `10` 条。
4. 非法页码或页大小参数使用安全兜底值，不返回 500。

### 详情子列表处理方式

项目详情、客户详情、销售详情中的子表格不再依赖 overview 接口一次性整包返回全量数据作为唯一数据源。

推荐做法：

- 为子表格提供独立的分页接口。
- overview 接口保留摘要信息，不承担所有子列表的全量返回责任。

原因：

1. 子列表独立分页后，接口职责清晰。
2. 后续如果增加筛选、排序、导出，不需要继续膨胀 overview 接口。
3. 可避免客户详情、项目详情在数据量大时一次请求过重。

### 接口口径要求

列表展示和搜索展示必须使用同一份业务口径，避免出现“列表能看到，搜索搜不到”的不一致问题。

例如：

- 如果设备中心列表中销售字段允许从“设备自身销售”回退到“最新项目销售”，搜索也必须覆盖同样的字段来源。

## 前端设计

### 通用分页状态

每个表格维护以下最小状态：

- `page`
- `pageSize`
- `total`
- `loading`
- `rows`

如果同一页面存在多个表格，则各自维护独立分页状态，不能共用一个页码。

### 通用请求模式

前端所有表格请求统一追加分页参数：

- `page`
- `page_size`

并从接口响应中统一读取：

- `results`
- `count`
- `page`
- `page_size`
- `total_pages`

### 通用组件策略

优先复用现有表格布局，在页面层抽取统一的分页处理逻辑，而不是一次性重构所有页面结构。

建议：

1. 先抽取轻量分页辅助方法或 composable，统一处理分页参数与响应。
2. 再在各页面底部挂接 Element Plus 分页组件。
3. 保持现有列表标题、搜索区、工具区结构不被打散。

### 页面级行为

1. 项目中心主列表
   - 搜索条件改变时重置到第一页。
   - 新增、编辑、删除项目后刷新当前页；若当前页越界则回退。
2. 客户中心右侧 tab 列表
   - 切换客户节点时，各 tab 分页重置。
   - 切换 tab 时，仅加载当前 tab 当前页数据。
3. 项目详情子列表
   - 打开详情抽屉时默认加载第一个 tab 的第一页。
   - 切换项目详情 tab 时按需加载，不一次性请求所有子列表分页数据。
4. 设备中心 / 销售中心 / 产品中心
   - 搜索、筛选、分页状态统一联动。

## 兼容与迁移策略

### 渐进式改造

为了符合“按模块开发、每完成一个模块单独提交”的要求，分页改造按以下顺序推进：

1. 后端统一分页基础能力
2. 项目中心分页
3. 客户中心分页
4. 设备中心分页
5. 销售中心分页
6. 产品中心 / 产品型号分页

### 兼容原则

1. 后端先提供统一分页能力。
2. 前端按模块逐步接入。
3. 某个前端页面未接入前，不影响其他已接入模块。
4. 所有搜索功能必须在分页接入后继续保持真实查询。

## 错误处理

1. 分页请求失败时，保留当前表格已有数据，不强制清空页面。
2. 在表格区域展示加载失败提示，并允许用户重试。
3. 当分页参数越界时，后端返回空结果或安全页，而不是抛异常。
4. 当前页无数据但总数仍大于零时，前端应尝试回退到有效页。

## 测试要求

### 后端

至少覆盖以下测试：

1. 默认分页返回第 `1` 页和默认 `page_size=10`
2. 指定 `page` 与 `page_size` 时返回正确结果
3. 搜索与分页叠加时总数和结果正确
4. 非法分页参数不会触发 500
5. 详情子列表分页接口能按所属对象正确过滤

### 前端

至少覆盖以下验证：

1. 主列表页码切换正确
2. 修改每页条数后刷新正确
3. 搜索后回到第一页且结果正确
4. 切换 tab / 详情对象后分页重置正确
5. 删除最后一条导致当前页为空时，自动回退页码正确
6. 前端构建通过

## 风险与取舍

### 风险

1. 当前部分详情页依赖 overview 接口整包返回数据，拆分子列表接口会带来前后端联动改造。
2. 某些页面如果同时存在搜索、筛选、分页、详情弹窗，状态管理容易混乱。
3. 统一分页后，旧页面对非分页响应结构的假设可能失效。

### 取舍

本次优先保证：

- 统一分页协议
- 统一交互行为
- 分模块渐进改造

本次不引入：

- 排序能力
- 列配置记忆
- 服务端缓存优化
- 无限滚动

这些能力可在统一分页落地后继续扩展。

## 结论

本方案采用“后端统一分页协议 + 前端统一分页交互 + 详情子列表独立分页接口”的实现方式，在不改动树结构浏览体验的前提下，为全系统所有表格提供可扩展、可维护的一致分页能力。
