# 项目架构与开发手册

> 目的：让新开发人员或后续 AI 在阅读本文件后，能够快速理解交付台的业务边界、数据关系、代码位置与开发约束。
>
> 最后整理：2026-07-28。涉及架构或核心业务规则变更时，必须同步更新本文件。

## 1. 项目定位

本项目是“交付台（Delivery Hub）”，用于统一管理客户、项目、设备、合同、产品型号、人员及设备交付后的维保服务。

核心原则：

- `Device` 表示一台真实、可长期追溯的物理/软件设备，序列号是其唯一身份。
- 设备可先后进入多个项目；新建项目、续保项目、下架记录均通过 `ProjectDevice` 保存，不复制设备主数据。
- 项目设备的服务周期、巡检、升级任务和运维记录必须绑定到对应的 `ProjectDevice`，从而区分同一设备的不同服务期。
- 用户看到的“当前项目/当前保内状态/签约主体”默认以该设备最新的项目设备绑定为准，排序依据为服务结束日期、更新时间、ID。

## 2. 技术架构

```text
浏览器
  └─ Vue 3 SPA + Element Plus（frontend，开发端口 5173）
       └─ Axios /api 请求，Token 鉴权
            └─ Django REST Framework（backend，开发端口 8000）
                 ├─ projects：交付业务与服务闭环
                 ├─ accounts：登录、RBAC、数据范围
                 └─ SQLite（当前开发库）
```

### 2.1 前端

- 技术：Vue 3、Vite、Vue Router、Pinia、Element Plus、Axios。
- 入口：`frontend/src/main.js`。
- 路由：`frontend/src/router/index.js`。
- 通用请求：`frontend/src/api/client.js`、`frontend/src/api/resources.js`。
- 鉴权：登录成功后将 DRF Token 保存为 `localStorage.pm_token`；Axios 自动添加 `Authorization: Token <token>`。
- API 地址：由 `frontend/src/utils/apiBaseUrl.js` 和环境变量决定；开发环境默认后端为 `http://127.0.0.1:8000/api`。

### 2.2 后端

- 技术：Django + Django REST Framework。
- 配置：`backend/config/settings.py`。
- 路由注册：`backend/config/urls.py`。
- 认证：DRF TokenAuthentication 和 SessionAuthentication；除登录接口外默认要求已登录。
- 业务应用：
  - `backend/projects/`：客户、项目、设备、合同、服务。
  - `backend/accounts/`：用户、角色、菜单、权限和数据范围。
  - `backend/core/models.py`：通用软删除基类。

### 2.3 数据库与文件

- 当前开发数据库：`backend/db.sqlite3`。
- 文件：设备基础信息图片、附件位于 `backend/media/`。
- 生产建议：迁移 PostgreSQL，并执行每日备份和异地备份；不能直接复制在线 SQLite 文件作为可靠备份方案。

## 4. 核心数据模型

除少数附件/权限模型外，业务模型继承 `BaseModel`，具备 `status`、`remark`、`extra`、创建/更新时间、创建/更新人、`is_deleted` 等字段。

### 4.1 主数据与组织关系

```text
Organization（组织树：客户、内部公司、厂商、代理等）
  └─ Person（销售、客户联系人、运维等）

ProductLine → Product → ProductVersion → DeviceModel → Device
```

| 模型 | 关键字段/规则 |
| --- | --- |
| `Organization` | `name`、`parent`、`org_type`、区域、地址；客户也使用本表。 |
| `Person` | 关联组织；`person_type` 区分销售、客户联系人、运维等。 |
| `SalesCustomerRelation` | 销售与客户的归属关系，是数据范围过滤的重要依据。 |
| `ProductLine/Product/ProductVersion/DeviceModel` | 产品目录树；`DeviceModel` 是设备型号字典。 |
| `Device` | `serial_number` 全局唯一；设备名称/型号、软硬件信息、系统版本、规则库版本、客户、销售、运维等。 |

设备表的重要约束：

- 序列号是设备去重标识。两个项目出现同一序列号时，仍是同一 `Device`。
- 产品型号和设备名称在 UI 中必须保持语义正确：设备型号来自 `DeviceModel`，设备名称/产品型号文字字段不可混淆。
- `software_version`、`rule_library_version` 是设备当前版本；运维升级记录可回写这两个字段。

### 4.2 项目、设备与服务周期

```text
Organization（客户） 1 ── n Project
Project 1 ── n ProjectDevice n ── 1 Device
ProjectDevice 1 ── 0..1 DeviceServicePlan 1 ── n DeviceServiceSchedule
```

| 模型 | 作用与关键字段 |
| --- | --- |
| `Project` | 项目编号、名称、客户、客户联系人、实际中标公司、对接公司、签约主体、销售、运维、阶段、金额、日期。 |
| `ProjectDevice` | 项目与设备的绑定，也是服务周期实体：部署位置、设备项目类型、用途、`service_type`、服务开始/结束、下架日期。 |
| `DeviceServicePlan` | 某一项目设备服务期的内部归属计划和规则快照；同一 `ProjectDevice` 只能有一个未删除计划。 |
| `DeviceServiceSchedule` | 具体服务项（巡检、系统升级、规则库升级）的独立频率、首次日期、提醒天数和是否自动建任务。 |

`ProjectDevice.service_type` 取值：

- `new_install`：新上设备。
- `renewal`：续保旧设备。
- `offline`：下架。

`Project.signing_subject` 取值：

- `direct`：直签。
- `agent`：代理。

项目编号规则：前端允许空；后端在创建项目时自动生成 `PRJ-YYYYMMDD-XXXX`。用户填写时保留其填写值。

### 4.3 服务、任务与运维闭环

```text
ProjectDevice
  └─ DeviceServicePlan（一个服务周期的内部归属）
       ├─ DeviceServiceSchedule（巡检/系统升级/规则库升级）
       │    └─ InspectionTask（通用服务任务，按计划日期生成）
       └─ DeviceOperationRecord（实际执行记录，可关联一个任务）
```

| 模型 | 关键规则 |
| --- | --- |
| `ServiceStandardTemplate` | 可复用服务标准：频率、间隔、提醒天数、服务内容。 |
| `DeviceServicePlan` | 存服务标准快照，避免后续模板变化影响已签约服务期。 |
| `DeviceServiceSchedule` | 一个计划内同一服务类型只能有一条未删除记录。 |
| `InspectionTask` | 虽沿用旧名称，现是通用服务任务；`task_type` 标记巡检/系统升级/规则库升级。一个服务项同一计划日期只能有一条未删除任务。 |
| `DeviceOperationRecord` | 运维执行事实；可关联一个任务，记录完成后将任务置为完成。系统/规则库升级可回写设备当前版本。 |

服务生成规则：

1. 创建服务计划时，按照 `service_contents` 创建支持的服务项，并按服务周期生成任务。
2. 新增服务项时，立即按该项频率生成任务。
3. 编辑服务项的类型、频率、间隔、首次日期、提醒或自动生成开关时：软删除未完成任务并重新生成；已完成任务保留历史。
4. 删除服务项时：软删除该项及其未完成任务；历史完成记录保留。
5. 删除运维记录时：若该记录关联的任务没有其他有效记录，任务恢复为待办或逾期。
6. 新增/编辑系统升级记录时，填写“升级后系统版本”会回写 `Device.software_version`；规则库版本同理。两个字段均非必填。

任务状态：`pending`（待办）、`completed`（完成）、`overdue`（逾期）、`cancelled`（取消）。

定时处理命令：

```powershell
cd backend
python manage.py process_inspection_tasks
```

该命令补齐服务任务、更新逾期状态并输出待提醒清单。生产环境应由操作系统计划任务或任务调度平台每日执行一次；开发环境可手工执行。

### 4.4 合同、附件与审计

```text
Project n ── n Contract（通过 ProjectContract）
Contract 1 ── n ContractParty
Contract 1 ── n ContractDevice n ── 1 Device
```

- `Contract`：合同编号、名称、最终客户、直接购买方、销售、金额、日期。
- `ProjectContract`：项目—合同关联。
- `ContractParty`：采购参与方链路及顺序。
- `ContractDevice`：合同设备、数量、价格。
- `Attachment`：泛型对象附件；项目附件经上传接口处理。
- `AuditLog`：只读审计日志接口。

## 5. 后端分层与接口规范

### 5.1 代码职责

| 文件/目录 | 职责 |
| --- | --- |
| `projects/models.py` | 数据模型、字段、索引、唯一约束。 |
| `projects/serializers.py` | 输入校验、业务写入、副作用（如生成任务、回写版本）。 |
| `projects/views.py` | ViewSet、查询条件、分页、概览接口、软删除流程。 |
| `projects/services.py` | 可复用领域逻辑：任务日期计算、任务生成、逾期刷新。 |
| `projects/management/commands/` | 可由命令行/计划任务运行的批处理。 |
| `accounts/services.py` | 销售数据范围过滤。 |
| `config/urls.py` | API 路由注册。 |

### 5.2 API 约定

- 统一前缀：`/api/`。
- 通用 CRUD：DRF Router 注册的资源遵循 `/api/<resource>/` 和 `/api/<resource>/<id>/`。
- 列表通常返回分页包：`count`、`page`、`page_size`、`total_pages`、`results`；组织树例外，返回全量数组。
- 前端使用 `listAllResource` 处理分页列表；使用 `createResource`、`updateResource`、`deleteResource` 统一写操作。
- 错误提示统一使用 `formatApiError`，不要把 Axios 异常直接展示给用户。

重要资源：

```text
organizations, people, sales-customer-relations
product-lines, products, product-versions, device-models, devices
projects, project-devices, service-standard-templates
device-service-plans, device-service-schedules, inspection-tasks, device-operation-records
contracts, project-contracts, contract-devices, contract-parties, attachments
users, roles, menus, permissions, user-roles
```

重要概览接口：

```text
GET /api/customers/{id}/overview/
GET /api/devices/{id}/overview/
GET /api/projects/{id}/overview/
GET /api/contracts/{id}/overview/
GET/POST /api/sales/{id}/customer-relations/
```

### 5.3 软删除、关联删除与查询

- 业务实体优先软删除（`is_deleted=True`），默认管理器只读取未删除数据。
- 不要用硬删除替代已有软删除流程。
- 删除服务计划/服务项/运维记录必须使用对应 ViewSet，不能直接在前端拼接或绕过关联处理。
- 为服务和项目查询增加过滤条件时，要明确是否按 `Device`、`ProjectDevice` 或当前服务周期查询，不能只凭序列号推断。

## 6. 前端开发规范

### 6.1 状态与组件

- 页面负责路由级数据加载和弹窗；可跨三个入口复用的业务界面必须沉淀成组件。
- 设备服务统一使用 `DeviceServiceWorkspace.vue`；不要在客户、项目、设备三个页面再次复制服务 UI。
- 设备详情只保留一个服务入口，避免外层和内层出现两套相同的服务计划/任务/记录页签。
- 表单字段必须在标签前体现必填性，并在提交前做前端校验；后端仍必须做最终校验。
- 选择已有设备、创建新设备、编辑项目设备必须分离流程。编辑已有绑定不得复用“选择已有设备”的新增界面。

### 6.2 列表与筛选

- 搜索区应有搜索、重置按钮；筛选项与搜索框在可用宽度内保持同一行。
- 列表数据由接口过滤时，筛选参数应由页面显式传入；前端本地筛选时，分页总数必须随筛选同步。
- “签约主体”等当前态字段应由后端基于最新项目设备绑定返回，前端只做显示映射。

### 6.3 UI 设计约束

- 同一概念只展示一次；例如服务计划总览不与服务项列表重复展示。
- 表格过宽优先调整列宽、展示层级或抽屉，不要让关键操作被横向滚动遮挡。
- 设备的服务项是用户可操作实体；内部服务计划仅作为服务期归属，不应让用户误认为是第二套数据。

## 7. 权限与数据范围

权限模型：

```text
User ── n UserRole n ── Role ── n Permission n ── Menu
User ── 1 UserAccessProfile ── n UserSalesScope ── Person（销售）
```

- 菜单权限控制前端路由访问与可见菜单。
- 权限动作：查看、新增、编辑、删除。
- 数据范围：全部、本人销售数据、自定义销售范围。
- 后端查询通过 `filter_queryset_by_sales_scope` 等方法过滤；新增查询接口时必须纳入同等数据范围判断，不能只在前端隐藏数据。

## 8. 本地运行、迁移与测试

### 8.1 启动

```powershell
# 后端
cd backend
python -m pip install -r requirements.txt
python manage.py migrate
python manage.py runserver 0.0.0.0:8000

# 前端（另开终端）
cd frontend
npm install
npm run dev
```

访问：

- 前端：`http://127.0.0.1:5173/` 或局域网 IP 加端口。
- 后端：`http://127.0.0.1:8000/`，API 为 `/api/`。

若局域网地址出现空白页，优先检查前端构建时 API 基地址、浏览器控制台网络错误与防火墙规则，不要只检查 Vite 是否启动。

### 8.2 数据库迁移

```powershell
cd backend
python manage.py makemigrations
python manage.py migrate
```

规范：

1. 先修改模型，再生成迁移；不要手工修改数据库结构替代迁移。
2. 新字段要明确是否允许空、默认值、索引、唯一约束和历史数据迁移策略。
3. 修改服务类模型时，验证现有计划、已完成任务和历史运维记录不会丢失。

### 8.3 测试命令

```powershell
# 后端完整回归
cd backend
python manage.py test

# 服务模块定向回归
python manage.py test projects.tests.DeviceServicePlanTests

# 前端测试与构建
cd frontend
node --test tests/*.test.js src/utils/*.test.js
npm run build
```

说明：前端当前采用 Node 内置测试，`package.json` 没有 `npm test` 脚本。新增纯函数或关键 UI 结构时，应在 `frontend/tests/` 或对应 `src/utils/*.test.js` 补充测试。

## 9. 标准开发流程

每个需求按以下顺序执行。

1. **确认领域边界**：先判断需求属于设备主数据、项目服务期、具体服务项、任务、运维记录还是展示层。涉及续保时，默认创建新的 `ProjectDevice`，不复制 `Device`。
2. **阅读现有实现**：至少检查相关 model、serializer、view、前端页面/组件、已有测试与迁移。
3. **设计数据变化**：先写清字段、关系、唯一约束、软删除和历史兼容策略；结构变化必须迁移。
4. **先后端后前端实现**：后端先建立校验和可测试接口；前端通过统一 API 工具接入，不复制业务逻辑。
5. **复用优先**：跨客户中心、项目中心、设备中心的功能优先抽为组件或服务，不做三份页面逻辑。
6. **验证关键路径**：至少覆盖新增、查询、编辑、删除、异常提示；服务模块还要覆盖任务生成、任务完成、版本回写与删除恢复。
7. **运行测试**：按改动范围执行定向测试；前端改动必须 `npm run build`，合并/发布前执行后端完整测试并记录已知失败。
8. **检查改动范围**：`git diff --check`、`git status --short`；不要误提交 `.env`、本地数据库、构建产物或用户已有草稿。
9. **提交与推送**：使用中文、准确的 Git 提交说明；提交前只暂存本需求相关文件，推送后记录提交哈希。
10. **同步文档**：改变架构、数据关系、服务规则、部署或测试命令时，更新本文件和必要的 API 文档。

## 10. 变更检查清单

### 涉及设备/项目

- [ ] 是否保持 `Device.serial_number` 的全局唯一语义？
- [ ] 是否应新增 `ProjectDevice` 而非复制设备？
- [ ] 是否正确处理新上、续保、下架和服务开始/结束日期？
- [ ] 当前签约主体、客户和项目的取值是否按最新绑定计算？

### 涉及服务

- [ ] 服务项是否绑定正确的 `DeviceServicePlan` 与 `ProjectDevice`？
- [ ] 频率或首次日期变更后，未完成任务是否重建？
- [ ] 已完成任务/运维记录是否被保留？
- [ ] 升级记录的版本回写是否符合业务预期？
- [ ] 是否避免在 UI 中重复展示内部服务计划与具体服务项？

### 涉及接口/前端

- [ ] 后端 serializer 是否有完整校验和错误信息？
- [ ] 查询是否接入销售数据范围？
- [ ] 前端是否有必填标识、提交前校验、加载态、错误提示和重置逻辑？
- [ ] 是否复用现有 API 工具、显示映射和公共组件？
- [ ] 是否新增或更新测试？

## 11. 已知维护注意事项

- 设备中心列表不会展示既没有客户、也没有项目绑定的孤立设备；相关测试数据需绑定客户或项目。
- 服务任务的模型名仍为 `InspectionTask`，但其 `task_type` 已支持系统升级和规则库升级；新增服务类型时需同步模型 choices、显示映射、任务生成和运维记录校验。
- `DeviceServicePlan` 仍是服务期的后端必需归属，但前端应以“服务项”为操作对象。
- 当前开发库为 SQLite；在迁移 PostgreSQL 前，不要把 SQLite 特定行为当成生产并发行为。
